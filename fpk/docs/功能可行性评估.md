## 2. ⚠️ 数据 / 元数据 / 同步 —— 卡在 CORS，FPK 同源代理可解

| 功能 | 数据源 | CORS | 判定 | 解法 |

| **每日放送·豆瓣源** | douban.com | ❌ 同上 | ⚠️ | 同上 |
| **B 站弹幕获取（含扫码登录）** | api.bilibili.com | ❌ **不支持** | ⚠️ | **必须**走 FPK 后端代理 |
| 年度观影报告（含导出长图） | 飞牛 API + canvas | 同源 | ✅ | 完全可行，导出用 canvas `toBlob` 下载 |

### 核心技术手段：FPK 同源代理端点

FPK 跑在飞牛自己的域名下（`https://<nas>/cgi/ThirdParty/fntvplus/index.cgi/...`），与影视页面**同源**，因此 payload 里的 `fetch` 天然不触发 CORS。

```
浏览器 payload
  └─ fetch('/cgi/ThirdParty/fntvplus/index.cgi/api/proxy?target=<b64url>&sign=<hmac>')
       └─ FPK Node 后端（root，可出网）→ 豆瓣 / B站 / Trakt OAuth
```

**必须加的防护**：白名单域名 + HMAC 签名 + 禁止内网地址（防 SSRF），否则等于给 NAS 开了个公开代理。

> 佐证：`danmakuWeb.ts` 文件头注释已经写明——*"数据通道用 ipcRenderer 是为了避免 https 页 fetch http 本地服务的 mixed-content/CORS 问题"*。也就是说**这个插件天生就是为网页端设计的**，只要把 `danmaku:prepare` 换成同源代理端点，它立刻能在浏览器里跑。

### 3.1 【重要澄清】「回传」有两种，别混淆

| | 谁传给谁 | 网页端能做吗 | 说明 |
|---|---|---|---|
| **A. 播放进度回传飞牛服务器** | 网页 → 飞牛 | ✅ **完全能，且比客户端简单** | 这才是通常说的「进度回传」，见下方实现 |
| B. 播放状态回传网页 | 本地播放器 → 网页 | ❌ 不能 | 仅在 `fntv://` 唤起 MPV 场景才有此需求，而 MPV 方案已整体划掉 |

**A 的确凿证据**（来自 Fntv-Plus 自身代码 `src/modules/fn_api/api.ts`）：

```ts
// 记录播放状态
recordPlayStatus(statusData: types.PlayStatusData): Promise<fn.ApiResponse<any>> {
    return fn.request(this.baseURL, '/v/api/v1/play/record', HttpMethod.POST, this.token, statusData);
}
// 标记已观看
setWatched(itemGuid): ...  POST /v/api/v1/item/watched  { item_guid }
```

- 路径是 **`/v/api/...`**，与影视页面**同源** → 无 CORS、无 mixed content
- `PlayStatusData`：`item_guid` / `media_guid` / `video_guid` / `audio_guid` / `subtitle_guid` / `play_link` / `ts`(秒) / 总时长
- 这些 guid 可从页面 URL 或 DOM 解析（`embyWall` 已在做同类解析）

**网页端实现只需几十行**：

```js
const video = document.querySelector('video');
let last = 0;
video.addEventListener('timeupdate', () => {
  const now = Date.now();
  if (now - last < 5000) return;          // 5 秒节流，与 PotPlayer 轮询节奏一致
  last = now;
  fetch('/v/api/v1/play/record', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ item_guid, media_guid, /* ... */ ts: video.currentTime, duration: video.duration })
  });
});
```

> **对比客户端**：客户端要跨进程从 MPV（JSON IPC）/ PotPlayer（potctl 轮询窗口）拿进度，再用 token 调 API；
> 网页端直接读 `video.currentTime`，**少了一整个跨进程层**。
> 认证方面，页面已在登录态内（Cookie / 页面内 token），无需额外处理。
| 倍速 / 音量跨集记忆 | ✅ | `playMemory.ts`，localStorage 即可 |
| 进度条悬停缩略图 | ✅ | `previewThumb.ts`，纯 DOM |
| 字幕自动选择 | ⚠️ | 需 hook 飞牛播放器内部字幕列表 API，属**逆向**，脆弱性高，建议降级为「记住上次选择」 |

## 4. ❌ 外部播放器 —— 网页端物理上做不到，只能绕道

| 功能 | 判定 | 原因 / 绕道方案 |
|---|---|---|
| MPV 播放（内置窗口） | ❌ | 需要本地进程 |
| PotPlayer 外挂播放 | ❌ | 需要本地进程 |
| MPV 着色器 / Anime4K / ICC | ❌ | 依附于 MPV |
| 硬解 H264/HEVC/VP9/AV1 | ❌ | 依附于 MPV（浏览器自身有硬解，但不受我们控制） |
| 直链 302 / NAS 代理双模式 | ❌ | 那是 Fntv-Plus 的 Go 代理（127.0.0.1:22346），浏览器访问不到 |
| MPV 上的弹幕 / 跳过 | ❌ | 依附于 MPV 脚本 |
| **「用 MPV 播放」按钮** | ⚠️ | **已决定 M4 做「单向遥控器」形态**（能调起即可，进度回传网页端搁置）：网页端点按钮 → 跳转 `fntv://play?guid=xxx` → 本地 Fntv-Plus 客户端接管播放。详见实施方案第七.5 节；可靠性 ~55% 已知，记入风险，不阻塞。 |

### 4.1 `fntv://` 协议唤起的可靠性评估（**结论：可行但不可靠，且大概率是伪需求**）

调用链路 5 步，**3 个断点**：

| 步骤 | 环节 | 状态 | 说明 |
|---|---|---|---|
| 1 | 网页点击 → `location = fntv://...` | ✅ | 必须在**用户手势内**触发，否则被弹窗拦截逻辑吞掉 |
| 2 | 浏览器确认弹窗 | ⚠️ | Chrome/Edge「要打开 Fntv-Plus 吗？」，**首次必弹**；Firefox 弹应用程序选择器，更糟 |
| 3 | 协议是否已注册 | ⚠️ | **JS 无 API 可探测**；Chrome 未注册时**静默失败、零提示**。只能靠 `blur`/`visibilitychange` 猜 |
| 4 | 客户端接管 → spawn MPV | ✅ | 客户端进程内全能力，MPV IPC / potctl / **进度回传飞牛照常工作** |
| 5 | 播放状态回传网页 | ❌ | 无回传通道；`https` 页调 `http://127.0.0.1` 会被 **mixed content** 拦截 |

**架构错配（本项目特有的痛点）**：
- MPV 现走 `node-mpv-2` 的 **JSON IPC 长连接**（`command('script-message', skip-metadata)`、`playlist-next`）
- PotPlayer 靠 `potctl` **每 5 秒轮询**窗口拿进度
- 协议唤起**只能传一次性 URL 参数，传不了长连接** → 网页端从此是黑盒（不知道播没起来、进度、失败）

> 缓解：客户端被唤起后可**自行重建**全部逻辑（第 4 步是可靠的），所以**核心的「进度回传飞牛」不会丢**，
> 丢的只是「网页端看不到实时状态」。

**该需求可能是伪需求**：

| 场景 | 用户状态 | 需要网页调起 MPV 吗 |
|---|---|---|
| 自己电脑 | 装了客户端 | **不需要**——客户端本来就能用 MPV |
| iPad / 手机 / 别人电脑 | 没客户端 | **用不了**——那台机器上没有 MPV |

网页端的真正价值是 UI 增强 + 网页播放器增强（弹幕/跳过/连播/进度回传），**这些在浏览器内全部闭环，不需要外部播放器**。
网页端与客户端是**互补，不是替代**。真需要打通的只有一个窄场景：在浏览器里逛、想看片时一键丢给 MPV。

**若要实现，只接受「单向遥控器」形态（不要假装双向）**：

```
网页端：点「用 MPV 播放」→ fntv://play?guid=xxx&server=<b64>&t=120
        toast「已发送到 Fntv-Plus」
        3s 内未失焦 → 提示「未检测到客户端，点此下载」
客户端：被唤起 → 自调飞牛 API 补全信息 → spawn MPV（现有逻辑不动）
```

客户端侧需补：`app.setAsDefaultProtocolClient('fntv')` + `second-instance` argv 解析（已有实例时）
+ electron-builder `mimeTypes` 配置。注意 Windows 上移动安装目录 / 绿色版会导致协议注册失效。

**已决定：M4 阶段做「单向遥控器」形态（能调起即可），进度回传网页端（B 类）先搁置。** 客户端侧参考实现见 `lc-1105-fntv-protocol.patch`；payload 侧只需在播放控制条加按钮（纯 DOM）。

## 6. 三个必须提前知道的风险

1. **DOM 结构漂移**：embyWall 5984 行的本质是在影视 SPA 上做 DOM 重构，影视一升级选择器就可能失效。
   → 好消息：网页端和客户端面对的是**同一份页面 DOM**，移植后维护成本与现在**完全相同**，不会更差。建议顺手加「DOM 断言 + 失败降级」。
2. **同源代理 = 新的攻击面**：必须域名白名单 + HMAC + 禁内网段，否则等于给 NAS 开公开代理（fndesk 就因为这类安全问题被做过安全测试）。
3. **飞牛 App / TV 端不生效**：它们走原生渲染，不是 WebView 加载 `/v`，注入对它们无效。能力边界要写清楚，避免用户误解。
