## 逐条说明

### (1) 基础要求

**按需使用、避免高频调用** — ✅

调用点严格绑定用户操作，没有任何定时轮询或后台预热：

| 触发时机 | 调用内容 |
|---|---|
| 用户点播放（进入播放页） | 该集一次匹配：搜索 1 + 弹幕 1 |
| 用户手动搜索 | 搜索 1（**不预拉弹幕**，用户选定后才拉） |
| 用户选定候选 | 该候选一次弹幕拉取 |

**额度保护（弹弹play 为兜底源）** — ✅ v1.11.1

配额有限，因此源链已改为 **自建源 → B站 → 弹弹play（兜底）**，弹弹play 只在
「前两个源都没拿到足量弹幕」时才被请求：

| 场景 | B站 | 弹弹play | 说明 |
|---|:---:|:---:|---|
| 自建源足量命中 | 0 | **0** | 完全不碰后两个源 |
| B站 足量命中 | 1 | **0** | 绝大多数播放走这条（B站免费） |
| B站 条数 < 下限 | 1 | 1 | 弹弹play 兜底探一次，更多才换 |
| B站 无匹配/该集无弹幕 | 1 | 1 | 同上 |
| 命中磁盘缓存 | 0 | **0** | 零上游请求 |

测试 `dandanplay_quota_test.go` 逐场景断言弹弹play 是否被调用；`TestDanmuPrepareNoRepeatUpstreamOnReplay`
断言重复播放不重复消耗。B站 侧候选最多试 3 个（`biliResolve`），避免「首位是低活跃剪辑」
时白白落到弹弹play —— 实测「葬送的芙莉莲」搜索结果首位仅 2 条弹幕，多试候选可显著减少兜底次数。

**条数下限（`danmuMinCount`，默认 100）** 直接决定兜底频率：命中条数 ≥ 该值即认为够用、直接返回，
低于才继续往下探。默认值由 20 提高到 100，让 B站 只拿到零星几条的集也去弹弹play 探一次
（弹幕体验更稳）；想省额度可调高，设 0 则「拿到多少算多少、不再往下探」。

单集请求量硬上限（测试 `TestDDPNoBulkScrapingPerEpisode` 钉住）：自动匹配路径最多
1 次搜索 + 3 次弹幕拉取（候选上限 3）+ 3 次分集兜底，合计 ≤7 次，**不随番剧库大小增长**。

播放预取：网页端在用户点击播放的瞬间并行预取该集弹幕（与播放器加载并行，这是体验必需，
不构成额外调用——不预取也要在播放开始后立刻拉）。

**缓存 API 返回数据** — ✅（v1.11.0 修复）

> ⚠️ 这是本次审计发现的**真实问题**，已修复：旧实现的磁盘缓存判断位于优选源链**之后**，
> 导致每次播放同一集都会重新调用上游（实测 4 次播放 = 4 次弹幕请求），缓存形同虚设。

修复后：

| 缓存层 | 粒度 | 时长 | 效果 |
|---|---|---|---|
| 弹幕磁盘缓存 | 标题+季+集 | 长期（无 TTL，命中即用） | 重复播放**零上游请求** |
| 搜索缓存 | 归一化标题 | 6 小时 | 换集复用，不重复搜索 |
| 分集缓存 | animeId | 6 小时 | 同上 |
| 薄弹幕集探测 | 标题+季+集 | 6 小时 | 低于下限的集不再反复重探上游 |

实测（`TestDanmakuPrepareNoRepeatUpstreamOnReplay`）：**4 次播放 → 上游弹幕请求 1 次**。
换集播放（`TestDanmakuPrepareSearchCacheAcrossEpisodes`）：2 集 → 搜索 1 次（缓存）、弹幕 2 次。

缓存时长取官方建议区间（一般数据 2–6 小时）中值；弹幕内容本身基本不变，磁盘缓存不设 TTL。
缓存只存本地（`@appdata/fntvplus/danmaku-cache/`），不上传、不共享。

**不用于违法/侵权** — ✅

仅读取公开弹幕数据用于播放展示；不采集用户信息、不上传任何数据到第三方。

### (2) 鼓励项

- **集成弹幕功能** — ✅ 本应用核心功能：飞牛影视网页原生播放器内注入 canvas 弹幕渲染，
  使用弹弹play 弹幕库提供多平台整合弹幕（实测《葬送的芙莉莲》首集 7310 条，
  含第三方站点整合源；不开 `withRelated` 仅 131 条）。
- **搜索 API 查找番剧** — ✅ 使用 `/api/v2/search/episodes`（自动匹配 + 手动搜索候选）。
- **文件识别 API（`/api/v2/match`）** — ➖ **未使用**，有意为之：
  该 API 需计算视频文件前 16MB 的 MD5，而本应用**不接触视频文件**——它是旁路反代，
  只从飞牛影视的元数据接口拿到「标题 / 季 / 集」再按标题匹配。
  这是架构约束（见 README「零文件改动」），同时也省去了上传文件哈希的调用。

### (3) 禁止项

**恶意行为 / 污染弹幕库** — ✅ 无相关能力

全链路**只有 GET 只读请求**（测试 `TestDDPOnlyReadOnlyEndpoints` 逐请求断言 HTTP 方法）。
未引用发送弹幕端点 `/api/v2/comment/{id}/app`，也没有任何 POST/PUT/DELETE 调用。
本应用是纯消费方，不具备写入弹幕库的能力。

**滥用 API / 规模化抓取** — ✅ 无相关行为

- 无「批量下载弹幕」：所有弹幕拉取都是**单集、按用户当前播放的那一集**，无遍历多集的循环
  （源码审查：`ddpFetchItems` / `biliFetchDanmakuXML` 调用点均为单集）。
- 无「下载数据库」：不遍历番剧列表、不批量拉取条目。
- 无爬虫式扫描：不调用任何列表/排行/全集枚举类接口。

**商业用途** — ⚠️ 需你确认

本应用为**开源个人项目**（README 声明「个人练手作品，非商业软件」），无收费、无广告、
无付费墙。但需注意两点：

1. 你的 AppId/Secret 以**内置凭证**形式随二进制分发，等于所有用户共用你的配额与责任。
   若应用后续有商业化计划，必须另行取得弹弹play 官方书面授权。
2. 官方配额页提到 2026-06-25 起实施分级配额制度，建议关注你账号下的额度上限
   （源码中的「备用 Secret 自动顺延」机制可在主密钥被限时维持可用，但不改变配额总量）。

## 内置凭证的合规提示

密钥申请与责任主体是你（应用持有者）。内置分发意味着：

- 所有用户的请求都记在你的 AppId 名下 —— 上述「按需调用 + 缓存 + 兜底降级」的修复因此**直接保护你的账号**；
  其中降级为兜底源这一项效果最直接：多数播放完全不会消耗弹弹play 额度；
- 备用 Secret（两个）用于主密钥被限时顺延，但**不扩大配额总量**，只是容错；
- 用户仍可填自己的 AppId/Secret 覆盖内置（设置面板 → 弹弹play），此时配额记在用户自己名下。
