## lc-1147 追修：选集列表整体左右游动（用户报「集数据容器变成左右移动了」）
根因：epListMerge 撑大视口时给了 ms `overflow-x:auto` 且 wmax 留了滚动余量 → 用户开着
「滚轮横向滚动」(wheelHScroll)，滚轮被转成 scrollLeft，整个竖排列表跟着左右滑。
两处修（epListMerge.ts widen）：
1. `overflow-x:hidden`——hidden 的 clientWidth 仍全宽（虚拟窗口照常覆盖整页），但不再给
   wheelHScroll 任何语义上的横滑容器；
2. wmax 宽度 = WIDE_MS_PX − ms 水平 padding（clientWidth 含 padding 而 scrollWidth = padding +
   内容宽，D 段 `padding:0 44px` 正好漏 88px 可程序化滚动游量——hidden 也拦不住
   scrollLeft 设值）。复验：scrollWidth==clientWidth==30000，强设 scrollLeft=500 恒 0，卡片不动。
removeEpListMerge 现在连 width/overflow/wmax 宽度一并清（缓存视图里不留 30000px 裁剪盒）。

## lc-1147 追修②：48 集后面又接 1~48（重复合并）
用户实测截图：列表到第 48 集后紧接着又是第 1、2、3 集。根因：合并成功后，导航钩子的
hard 重试链（embyWall.ts 还有 [600,1500,3000] 延迟补充调度）会再次 ensure(hard=true)，
hard 绕过 mergedValid/冷却 → 再跑一遍 runMerge，而 runMerge 复用已挂载的旧容器 append
→ 1~48 接 1~48。修（epListMerge.ts）：
1. runMerge 永远构建**全新容器**，成功后拆旧上新（原子换，失败回退原生，绝不 append 旧容器）；
2. ensure 入口成功合并后 8s 冷却对 hard/soft 一视同仁（重试链/延迟调度/观察器全部短路）；
3. 克隆时按集 guid 去重兜底（某页挂载混入上一页残卡也不会重复入列）。
复验：合并后连打两次 ensure(true)，容器恒 48 张、48 唯一链接。

## lc-1159 appDialog「按钮点了没反应 / 关不掉」真因 = Electron sandbox

- 现象：中文安装路径下启动（装完 EB 会自动拉起程序）弹「安装路径不兼容」，**两个按钮都点不动**，
  窗口 alwaysOnTop 又关不掉，用户被锁死。
- **真因**：Electron 20+ 渲染进程默认 `sandbox: true`，**沙箱下 `nodeIntegration: true` 被静默忽略**
  → 页内内联脚本 `require('electron')` 抛错 → 外层 `try/catch` 吞掉 → 按钮监听注册了但 `send()`
  不发出，Esc 同理失效。叠加该窗口 `frame:false`(无系统关闭钮) + `alwaysOnTop` + `skipTaskbar`
  (任务栏也找不到) → 只能 Alt+F4/任务管理器。
- 修：`webPreferences` 显式 `sandbox: false`（该弹窗 HTML 即时生成写临时文件、**没有 preload**，
  只能走 nodeIntegration；主窗口有 preload 走 preload 通道不受影响）+ 右上角补「✕」关闭入口。
- **验证手法（可复用）**：Playwright 加载 `buildAppDialogHtml()` 的真实产物 + `addInitScript`
  注入 mock `require`/`ipcRenderer`，点击后回读调用记录。
  ⚠ 坑：`page.setContent()` **不会**触发 `addInitScript`（不走导航）→ 必须写临时 HTML 再
  `page.goto('file:///...')`，否则注入的 mock 不存在、测出来是假失败。
- 触发链备忘：`src/main/main.ts` 的 `checkNonAsciiPathBlocking()`（whenReady 内、主窗未建前）
  → `appDialog({title:'安装路径不兼容'})`。它是**应用**弹的，不是 NSIS 安装器（原生程序跑不了 Electron 代码）。
- ⚠ **并行会话**：工作区里另有一条提交线（lc-1147~1157）和它的调试脚本 `scripts/_ad_*.js`，
  同一个 appDialog.ts 被两边同改；本次编号顺延为 lc-1159 避让，并把其未提交的 lc-1158 改动一并提交。

## lc-1163 appDialog「三个按钮全点不动」的真因与正解

- **真因**: Windows 对**没有父窗口的顶层窗口**抢前台有硬限制(`SetForegroundWindow` 只允许当前前台
  进程或刚启动的进程)。本弹窗出现在**主窗口尚未创建**的启动期 = 「孤儿窗」: 可见、命中测试指向它、
  Electron 自报 focused=true, 但**拿不到前台焦点**(`isForegroundNow=False`)、**页面 0 个鼠标事件**。
- **正解**: 启动期(无可见窗口)改用原生 `dialog.showMessageBox`; 有可见窗口时仍用自绘玻璃窗。
- **弯路清单(别再走)**: `sandbox:false` → `nodeIntegration+contextIsolation:false` →
  preload+contextBridge → `transparent:false` → `alwaysOnTop('screen-saver')` —— **全无效**,
  因为根因不在渲染层配置, 而在「窗口能否成为前台」。
  ⇒ **教训: 「事件到了但按钮没反应」先查窗口是否真在前台(Win32 视角), 别急着改渲染层。**
- 诊断工具: Python ctypes 直接看 Win32 视角 —— `GetForegroundWindow()==hwnd?`、
  `WindowFromPoint()` 命中谁、`GetWindowLongW(GWL_EXSTYLE)`、原生按钮枚举 + `mouse_event` 真实点击。
  比在 Electron 里猜有效得多。

## lc-1164 全屏弹幕修复（15:2x）
- 用户报障：飞牛原生网页播放，点右下角全屏后**弹幕整层不显示**。
- **根因**：弹幕 canvas(z-index:5)/高能条 canvas(z-index:6) 挂在 body 下 fixed；全屏时播放器成独立渲染子树
